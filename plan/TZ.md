# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## на разработку программного обеспечения «Red-Bot» — автоматизированной системы алгоритмической торговли на базе T-Bank Invest API

**Версия документа:** 1.0
**Статус:** Утверждено к разработке

---

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Наименование системы
Условное наименование — **Red-Bot**. Программное обеспечение автоматизированной алгоритмической торговли инструментами Московской биржи через T-Bank Invest API.

### 1.2. Назначение документа
Настоящее ТЗ фиксирует согласованные архитектурные, функциональные и технологические решения проекта, определяет структуру системы, границы модулей, соглашения об именовании и порядок разработки. Документ является обязательным к исполнению при разработке; любое отклонение от зафиксированных решений требует явного пересмотра ТЗ.

### 1.3. Заказчик и исполнитель
Единый заказчик и разработчик (индивидуальный проект). Разработка ведётся силами одного человека на персональном компьютере без выделенной серверной инфраструктуры.

### 1.4. Термины и сокращения

| Термин | Определение |
|---|---|
| ТА | Технический анализ |
| ТП / TradePlan | Торговый план — доменная сущность гипотезы сделки с параметрами входа, выхода, инвалидации |
| MFE | Maximum Favorable Excursion — максимальная нереализованная прибыль сделки |
| MAE | Maximum Adverse Excursion — максимальная нереализованная просадка сделки |
| Confluence score | Агрегированный числовой показатель совпадения сигналов нескольких индикаторов/фреймов |
| Тезис / Thesis | Формализованная гипотеза входа, положенная в основу торгового плана |
| Инвалидация тезиса | Событие, при котором условия, обосновавшие вход, перестают быть верными, независимо от текущей цены |
| Hard stop | Аварийный стоп-лосс по цене, действующий всегда без исключений |
| Walk-forward | Методология валидации стратегии, при которой параметры настраиваются на одном сегменте данных и проверяются на другом, не участвовавшем в настройке |
| Hot/Warm/Cold | Уровни хранения данных по давности и частоте обращения |
| Порт (Port) | Контракт (`typing.Protocol`) взаимодействия ядра с внешним миром |
| Адаптер (Adapter) | Конкретная реализация порта под определённую технологию |
| Driving / Driven | Направление зависимости адаптера: управляющий системой / управляемый системой |
| IMOEX | Индекс Московской биржи, используется как эталонный (benchmark) инструмент |

## 2. НАЗНАЧЕНИЕ И ЦЕЛИ СОЗДАНИЯ СИСТЕМЫ

### 2.1. Назначение
Система предназначена для автоматизированного анализа рыночных данных ограниченного набора инструментов Московской биржи, формирования и исполнения торговых решений в свинг/интрадей-горизонте, а также для непрерывного накопления структурированных данных о собственных решениях с целью последующего статистического самоанализа эффективности.

### 2.2. Цели
1. Снизить издержки на комиссию за счёт отбора только тех точек входа/выхода, где ожидаемое движение существенно превышает совокупные транзакционные издержки.
2. Устранить эмоциональную составляющую принятия торговых решений за счёт формализованных, воспроизводимых правил.
3. Обеспечить полную прозрачность и объяснимость каждого решения бота для последующего аудита пользователем.
4. Накопить статистически значимую базу собственных решений для выявления систематических слабых мест стратегии.
5. Обеспечить архитектуру, допускающую последующее расширение (новые индикаторы, новые инструменты, новые адаптеры) без переработки ядра системы.

### 2.3. Не входит в цели проекта (явные ограничения)
- Высокочастотная (HFT) торговля, торговля с горизонтом удержания менее часов.
- Торговля в шорт, использование заёмных средств/плеча.
- Использование машинного обучения промышленного масштаба, требующего GPU/облачных мощностей.
- Автоматическое самоизменение торговой логики без подтверждения пользователем.
- Разметка волн Эллиотта и гармонических паттернов XABCD (сознательно отложено как избыточно субъективная методология).

## 3. ОБЩИЕ ТРЕБОВАНИЯ К АРХИТЕКТУРЕ

### 3.1. Архитектурный стиль
Система строится по принципу **гексагональной архитектуры (Ports & Adapters)** с чётким разделением на 4 логических блока:

| Блок | Ответственность | Внешние зависимости |
|---|---|---|
| `config/` | Bootstrap-конфигурация, секреты, валидация запуска | pydantic-settings, keyring |
| `core/` | Доменная модель, торговая логика, риск-модуль, ТА, порты | Только стандартная библиотека |
| `application/` | Оркестрация use case, DI-композиция, конкурентность | Зависит от `core`, не зависит от `adapters` напрямую |
| `adapters/` | Интеграции: T-Bank API, БД, Web GUI, CLI | grpc, duckdb, fastapi и т.д. |

### 3.2. Направление зависимостей (незыблемое правило)

```
config → application → core
adapters → core (implements ports)
adapters → application (calls use cases)
core → НИЧЕГО из внешних слоёв
```

`core/` не имеет права импортировать что-либо из `adapters/`, `application/` или `config/`. Нарушение этого правила является критическим дефектом архитектуры и подлежит немедленному исправлению независимо от стадии разработки.

### 3.3. Принцип «разумной достаточности портов»
Порт создаётся исключительно тогда, когда для него существует или заведомо в ближайшей перспективе появится вторая независимая реализация. Зафиксированный и закрытый (не расширяемый произвольно) перечень портов:

`MarketDataPort`, `OrderExecutionPort`, `RepositoryPort`, `ArchivePort`, `ClockPort`, `NotificationPort`.

Расширение данного перечня допускается только по явному обоснованию через пересмотр ТЗ.

### 3.4. Порты — контракт реализации
Все порты объявляются как `typing.Protocol`. Наследование от `abc.ABC` не используется. Соответствие адаптера порту определяется структурно — совпадением сигнатур методов.

## 4. ТРЕБОВАНИЯ К ТЕХНОЛОГИЧЕСКОМУ СТЕКУ

| Область | Технология | Обоснование |
|---|---|---|
| Язык | Python ≥ 3.14 | Структурная конкурентность `TaskGroup`, поддержка free-threading для CPU-bound расчётов |
| API-клиент | `t-tech-investments` (официальный SDK) | Актуальная замена устаревшего `tinkoff-investments` |
| Web-фреймворк | FastAPI + WebSocket | Асинхронность, совместимость с asyncio-ядром бота |
| Хранилище | DuckDB (hot/warm) + Parquet (cold) | Встраиваемая аналитическая БД без выделенного сервера, эффективные колоночные запросы |
| Конфигурация | pydantic-settings + DuckDB operational settings | Токен/ресурсы валидируются Settings; режим и account defaults сохраняются приложением и меняются из GUI/CLI, `.env` не обязателен |
| Секреты | `keyring` (API-токен) или secret manager/ENV для deployment | Токен не хранится в DuckDB, коде, тестах, логах или Git |
| Тестирование | pytest, contract-тесты между адаптерами | Гарантия взаимозаменяемости адаптеров одного порта |
| Линтинг/типизация | ruff, mypy strict | Единый стиль кода, статическая проверка типов |
| Логирование | structlog с маскированием секретов | Структурированные логи, защита токенов |

## 5. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 5.1. Модуль сбора рыночных данных (FR-1)

- **FR-1.1.** Система обеспечивает получение исторических и потоковых котировок по 2–5 сконфигурированным инструментам плюс опционально IMOEX как эталонному инструменту.
- **FR-1.2.** Данные собираются по трём таймфреймам: 1D, 1H, 1m. Для 1D/1H допустим режим периодического опроса; для 1m и стакана — постоянная потоковая подписка.
- **FR-1.3.** При обрыве потокового соединения система обязана автоматически переподключиться и заново переподписаться на весь актуальный список подписок, без потери непрерывности анализа.
- **FR-1.4.** Транзиентные ошибки соединения (`UNAVAILABLE`, `DEADLINE_EXCEEDED`) обрабатываются автоматическими повторными попытками с экспоненциальной задержкой; ошибки аутентификации повторным попыткам не подлежат и эскалируются немедленно.
- **FR-1.5.** Все ценовые значения конвертируются из формата API (units/nano) в тип `Decimal` на границе адаптера; использование `float` для денежных величин в торговой логике запрещено.
- **FR-1.6.** При расчёте стоимости позиции обязателен учёт размера лота инструмента, так как котировки предоставляются в расчёте на одну ценную бумагу.

### 5.2. Модуль технического анализа (FR-2)

- **FR-2.1.** Система использует индикаторы, предоставляемые API (SMA, EMA, RSI, MACD, полосы Боллинджера), через единый порт получения данных.
- **FR-2.2.** Система реализует собственные индикаторы, не предоставляемые API: ATR, объёмные индикаторы (OBV, VWAP), уровни Фибоначчи, корреляция с IMOEX (бета, относительная сила), анализ дисбаланса стакана.
- **FR-2.3.** Каждый индикатор реализует единый программный контракт (`Indicator` Protocol), что обеспечивает добавление нового индикатора без изменения существующего кода анализа — только регистрацией новой реализации.
- **FR-2.4.** Параметры индикаторов (периоды, множители) конфигурируются раздельно для каждого таймфрейма и каждого инструмента, с сохранением истории версий изменений.
- **FR-2.5.** Волновой анализ Эллиотта и гармонические паттерны XABCD **исключены** из объёма разработки текущей версии.
- **FR-2.6.** Реализуется агрегирующий модуль confluence-скоринга, сводящий сигналы всех индикаторов и всех таймфреймов в единый числовой показатель уверенности.

### 5.3. Модуль стратегии (FR-3)

- **FR-3.1.** Анализ выполняется по принципу «сверху вниз»: 1D формирует общий рыночный контекст (bias, режим рынка), 1H формирует и подтверждает торговый сетап, 1m совместно со стаканом определяет точный момент входа.
- **FR-3.2.** Сигнал младшего таймфрейма не может инициировать вход, противоречащий контексту, установленному на 1D, за исключением случаев, когда контр-трендовая торговля явно разрешена конфигурацией.
- **FR-3.3.** Результатом работы модуля стратегии является доменная сущность `TradePlan`, содержащая: цену входа, цену hard stop, целевую цену, структурированную гипотезу (`TradeThesis`) с деревом обоснования (`reasoning_chain`), правило инвалидации тезиса, максимальное время удержания позиции (TTL).
- **FR-3.4.** Стратегия работает только в направлении LONG. Функциональность коротких позиций не реализуется в текущей версии.

### 5.4. Модуль риск-менеджмента (FR-4)

- **FR-4.1.** Любой торговый план обязан пройти проверку модулем издержек: ожидаемая целевая доходность обязана превышать совокупные транзакционные издержки (комиссия за цикл сделки, ожидаемое проскальзывание) с настраиваемым коэффициентом запаса (по умолчанию не менее чем в 2 раза).
- **FR-4.2.** Размер позиции рассчитывается на основе фиксированного процента риска от капитала на сделку, с учётом лотности инструмента.
- **FR-4.3.** Реализуются три независимых, одновременно активных механизма защиты открытой позиции:
  - **Hard stop** — по цене, действует всегда без возможности отключения из GUI;
  - **Инвалидация тезиса** — по условию, специфичному для конкретной гипотезы входа, проверяется на каждом цикле анализа для открытой позиции;
  - **Выход по времени (Time exit)** — принудительное закрытие позиции при превышении TTL, если ни один из целевых уровней не достигнут.
- **FR-4.4.** Торговля выполняется исключительно с одним заранее выделенным торговым счётом (`managed_account_id`). Отправка любой команды на иной счёт технически невозможна и блокируется на уровне адаптера исполнения ордеров.

### 5.5. Модуль анализа стакана (FR-5)

- **FR-5.1.** Система получает снимки биржевого стакана с настраиваемой глубиной.
- **FR-5.2.** Рассчитываются дисбаланс объёма (bid/ask imbalance) и текущий спред.
- **FR-5.3.** Данные стакана используются исключительно как фильтр точного момента входа на минутном таймфрейме, не как самостоятельный источник торговых сигналов.
- **FR-5.4.** При аномально широком спреде относительно исторической нормы формирование входа блокируется риск-модулем.

### 5.6. Модуль межинструментального анализа (FR-6)

- **FR-6.1.** IMOEX используется как эталонный, не торгуемый ботом инструмент.
- **FR-6.2.** Для каждого торгуемого инструмента рассчитываются скользящая бета к IMOEX и показатель относительной силы.
- **FR-6.3.** Отклонение поведения инструмента от эталонного индекса (опережение/отставание) учитывается как один из факторов confluence-скоринга.

### 5.7. Модуль журналирования и самоанализа (FR-7)

- **FR-7.1.** На каждом цикле анализа, независимо от итогового решения (включая решение бездействовать), формируется исчерпывающий снимок рыночных данных (`MarketSnapshot`), включающий: котировки по всем таймфреймам, все рассчитанные значения индикаторов, полный снимок стакана, состояние корреляции с IMOEX, определённый рыночный режим.
- **FR-7.2.** Каждое принятое решение фиксируется как `DecisionSnapshot`, включающий пошаговую цепочку обоснования (`reasoning_chain`) с указанием вклада каждого модуля анализа, итоговый confluence score, результат проверки риск-модулем, человекочитаемое текстовое пояснение решения.
- **FR-7.3.** Для каждой закрытой сделки рассчитываются: MFE, MAE, эффективность выхода (доля от MFE, зафиксированная как реальная прибыль), а также показатель постэкзитного дрейфа цены (сравнение цены выхода с ценой закрытия сессии и через 1–3 дня после закрытия сделки).
- **FR-7.4.** На основе накопленной истории сделок система автоматически формирует статистические гипотезы о систематических слабых местах стратегии (например, зависимость результата от диапазона значений индикатора на входе).
- **FR-7.5.** Ни одна гипотеза не переходит в статус подтверждённой без прохождения валидации по методологии walk-forward на исторических данных, не участвовавших в формировании гипотезы.
- **FR-7.6.** Применение подтверждённой гипотезы к боевым параметрам стратегии выполняется исключительно вручную, по явному подтверждающему действию пользователя в GUI. Автоматическое самоизменение стратегии запрещено.
- **FR-7.7.** Минимальный размер выборки для формирования гипотезы — параметр конфигурации, значение по умолчанию — 30 сделок.

### 5.8. Модуль исполнения ордеров (FR-8)

- **FR-8.1.** Система поддерживает три независимых, взаимозаменяемых контура исполнения: боевой (LIVE), песочница (SANDBOX), историческая симуляция (BACKTEST) — реализуемые как разные адаптеры одного порта.
- **FR-8.2.** Переключение контура исполнения не требует изменения кода торговой логики — используется единый программный сценарий цикла анализа для всех трёх режимов.
- **FR-8.3.** Симулированный контур бэктеста обязан моделировать: комиссию, идентичную боевой ставке, проскальзывание, реалистичное условие заполнения лимитных ордеров (только при фактическом прохождении ценой уровня заявки в исторических данных).
- **FR-8.4.** Контур песочницы используется для проверки корректности интеграции с API, а не для итоговой оценки качества стратегии, ввиду возможных отличий от реалистичного исполнения на бирже.

### 5.9. Модуль хранения данных (FR-9)

- **FR-9.1.** Все данные хранятся персистентно на диске. Запрет на чисто оперативную (`in-memory`) конфигурацию хранилища.
- **FR-9.2.** Потребление оперативной памяти хранилищем ограничивается явно заданным конфигурационным лимитом, не допускающим значимого влияния на производительность ПК при параллельном использовании пользователем в течение дня.
- **FR-9.3.** Реализуется многоуровневое хранение: «горячий» слой (текущий торговый день), «тёплый» слой (несколько месяцев истории), «холодный» слой (партиционированный сжатый архив, неограниченный горизонт хранения).
- **FR-9.4.** Перенос данных между уровнями хранения выполняется автоматической фоновой задачей по расписанию и/или при достижении настраиваемого порога занятого места на диске.
- **FR-9.5.** Портфель и состояние счёта хранятся как перезаписываемый снимок текущего состояния. История закрытых сделок хранится как неизменяемый (append-only) журнал.

### 5.10. Web GUI (FR-10)

- **FR-10.1. Дашборд**: индикация активного контура исполнения (LIVE/SANDBOX/BACKTEST), список активных торговых планов с показателями текущего MFE/MAE, лента решений бота в реальном времени, статус потоковых соединений с API.
- **FR-10.2. Управление инструментами**: добавление/удаление/редактирование торгуемых инструментов и эталонного инструмента (IMOEX) без изменения кода.
- **FR-10.3. Управление параметрами ТА**: редактирование параметров индикаторов раздельно по инструменту и таймфрейму с сохранением истории версий изменений.
- **FR-10.4. Управление риск-параметрами**: редактирование процента риска на сделку, коэффициента запаса над издержками, параметров TTL, отображение и защита поля идентификатора торгового счёта от случайного изменения.
- **FR-10.5. Графический анализ**: отображение свечей, наложенных индикаторов, уровней Фибоначчи, меток входа/выхода, визуализация зоны MFE/MAE, переключение между таймфреймами.
- **FR-10.6. Журнал и самоанализ**: просмотр ленты снимков решений с фильтрацией по статусу, статистические распределения показателей эффективности выхода и постэкзитного дрейфа, интерфейс ручного подтверждения применения гипотезы.
- **FR-10.7. Прогон бэктеста**: выбор периода и набора инструментов, выбор режима (простой/walk-forward), сравнительное отображение кривой доходности на обучающем и проверочном сегментах данных.
- **FR-10.8. Администрирование хранилища**: визуализация занятого объёма по уровням хранения, ручной запуск архивации, консоль выполнения read-only SQL-запросов для произвольного анализа накопленных данных, управление политикой хранения (сроки, пороги), функция резервного копирования и восстановления.
- **FR-10.9. Безопасность и служебные функции**: кнопка аварийной остановки новых входов (kill-switch), журнал аудита действий пользователя в GUI, управление токеном доступа к API без отображения его значения после ввода.

## 6. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 6.1. Надёжность
- **NFR-1.** Сбой одного фонового процесса (например, временная недоступность потока котировок) не должен приводить к остановке других фоновых процессов, в частности — процесса мониторинга открытых позиций и риск-контроля, который обязан работать непрерывно.
- **NFR-2.** Все фоновые долгоживущие циклы обязаны быть самовосстанавливающимися — при возникновении необработанного исключения цикл логирует ошибку и перезапускается после паузы, а не завершает работу процесса.
- **NFR-3.** При некорректной или небезопасной конфигурации (например, попытка отключить проверку TLS-сертификата в боевом режиме) процесс обязан немедленно завершиться с диагностическим сообщением при старте, не выполняя ни одного сетевого вызова.

### 6.2. Безопасность
- **NFR-4.** Токен доступа к API в боевом режиме не хранится в открытом текстовом файле — используется системное защищённое хранилище учётных данных операционной системы.
- **NFR-5.** Любые поля конфигурации, содержащие секретные значения, типизируются как защищённые от случайного вывода в лог или отладочную печать.
- **NFR-6.** Соединение с API устанавливается с проверкой подлинности сертификата через актуальный доверенный корневой сертификат; полное отключение проверки сертификата доступно только в режиме локальной разработки и технически заблокировано в боевом режиме.
- **NFR-7.** Исполнение ордеров технически ограничено единственным выделенным торговым счётом, изолированным от иных инвестиционных позиций пользователя.

### 6.3. Производительность и ресурсоёмкость
- **NFR-8.** Полный цикл анализа по всем сконфигурированным инструментам и таймфреймам обязан укладываться в единицы секунд на типовом персональном компьютере.
- **NFR-9.** Потребление оперативной памяти системой хранения ограничено явным конфигурационным лимитом и не должно создавать ощутимой нагрузки на ПК при параллельном использовании пользователем в течение рабочего дня.
- **NFR-10.** Тяжёлые вычисления (полный прогон бэктеста, walk-forward валидация гипотез) не блокируют основной цикл анализа и мониторинга позиций.

### 6.4. Расширяемость (сквозное требование проекта)
- **NFR-11.** Добавление нового технического индикатора не должно требовать изменения кода вне модуля данного индикатора и точки его регистрации.
- **NFR-12.** Добавление нового инструмента или изменение параметров технического анализа выполняется исключительно через GUI, без вмешательства в код и без перезапуска процесса, где это технически осуществимо.
- **NFR-13.** Добавление нового внешнего адаптера (например, альтернативного источника данных) не должно требовать изменения доменной логики ядра — только реализации существующего порта.

### 6.5. Тестируемость
- **NFR-14.** Доменная логика (`core/`) обязана быть тестируема полностью без сетевых вызовов и обращений к диску — за счёт передачи фиктивных реализаций портов.
- **NFR-15.** Для каждого порта, имеющего более одной реализации, обязателен единый набор контрактных тестов, гоняемых против всех реализаций для гарантии их взаимозаменяемости.
- **NFR-16.** Любые проверки, зависящие от времени выполнения (TTL, тайм-ауты), обязаны быть детерминированно тестируемыми через управляемую фиктивную реализацию порта времени.

## 7. ТРЕБОВАНИЯ К ДАННЫМ

### 7.1. Разделение конфигурации
Строго разграничиваются:
- **Bootstrap-секреты и ресурсы** (`config/`) — токен, TLS и лимиты процесса. Токен по умолчанию хранится в системном keyring; environment/`.env` — необязательные overrides для развёртываний. Секреты не записываются в DuckDB или Git.
- **Пользовательские и операционные настройки** (DuckDB) — execution mode по умолчанию, отдельный счёт для каждого режима, список инструментов и риск-настройки. Редактируются из GUI/CLI; режим и счёт применяются после рестарта, стратегии и другие runtime-параметры — согласно их use case. Режим/счёт не требуют ручного `.env`.

### 7.2. Типизация данных
- Все денежные величины и цены — тип `Decimal`. Использование `float` для расчётов, влияющих на торговые решения, запрещено.
- Все статусы и перечисляемые категории — `enum.StrEnum`, обеспечивающий совместимость со строковым представлением при сохранении типобезопасности.
- Все временные метки — `datetime` с явным указанием часового пояса.

### 7.3. Модель хранения
- Реляционно-аналитическая встраиваемая СУБД для «горячего» и «тёплого» слоёв.
- Колоночный сжатый партиционированный формат для «холодного» архива, партиционирование по инструменту и календарному периоду.
- Вложенные структурированные данные (цепочки обоснования решений, полные снимки индикаторов) допускается хранить в нативном полуструктурированном формате (JSON-колонки) без обязательной полной нормализации, при условии сохранения возможности выполнения аналитических запросов по вложенным полям.

## 8. ЭТАПЫ РАЗРАБОТКИ

### Этап 1 — Фундамент
Настройка `config/`, доменная модель `core/domain`, объявление всех портов, базовая структура проекта, TLS-интеграция.

### Этап 2 — Данные и хранение
Реализация `DuckDBRepository`, `ParquetArchiveAdapter`, адаптеров получения рыночных данных (sandbox-контур в первую очередь), базовый конвейер сбора и сохранения `MarketSnapshot`.

### Этап 3 — Технический анализ и стратегия
Реализация собственных индикаторов, confluence-скоринга, мультитаймфреймовой логики стратегии, формирования `TradePlan`.

### Этап 4 — Риск-модуль и исполнение
Реализация всех механизмов защиты позиции (hard stop, инвалидация тезиса, time exit), интеграция исполнения ордеров в песочнице.

### Этап 5 — Backtest
Реализация симулированного контура исполнения, walk-forward методологии, полной переиспользуемости цикла анализа между режимами.

### Этап 6 — Журналирование и самоанализ
Реализация полной модели снимков решений, расчёта MFE/MAE/постэкзитного дрейфа, движка формирования и валидации гипотез.

### Этап 7 — Web GUI
Реализация всех разделов интерфейса согласно п. 5.10, включая администрирование хранилища и SQL-консоль.

### Этап 8 — Комплексное тестирование и пилотный запуск
Продолжительная эксплуатация в контуре песочницы, накопление статистически значимой истории решений, только после этого — рассмотрение перехода в боевой режим.

## 9. ПОРЯДОК КОНТРОЛЯ И ПРИЁМКИ

- Каждый модуль ядра принимается только при наличии полного набора юнит-тестов без внешних зависимостей.
- Каждый порт с несколькими реализациями принимается только при наличии и успешном прохождении контрактных тестов против всех реализаций.
- Переход в боевой режим исполнения ордеров признаётся допустимым только после: (а) продолжительной безаварийной работы в контуре песочницы, (б) наличия положительного результата walk-forward валидации стратегии на исторических данных, (в) явного осознанного решения пользователя, зафиксированного включением боевого режима в конфигурации.

## 10. ОГРАНИЧЕНИЯ И ДОПУЩЕНИЯ

- Система рассчитана на эксплуатацию одним пользователем на одном персональном компьютере, без требований к масштабированию на несколько узлов.
- Система не предназначена для использования заёмных средств и коротких позиций в текущей версии.
- Используемые методы технического анализа ограничены методологиями с разумным уровнем формализуемости; методики, требующие субъективной экспертной разметки (волновой анализ Эллиотта, гармонические паттерны), исключены из объёма разработки.
- Достоверность результатов бэктеста и песочницы признаётся ограниченной относительно реального рыночного исполнения; окончательная оценка эффективности стратегии производится по результатам эксплуатации в боевом режиме на статистически значимой выборке сделок.
