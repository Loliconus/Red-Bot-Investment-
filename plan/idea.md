## ЧАСТЬ I. ПРОДУКТОВЫЕ РЕШЕНИЯ

### 1.1. Торговый профиль
- **Стиль**: гибрид свинг/интрадей. Горизонт удержания позиции — от часов до нескольких дней. Скальпинг и HFT исключены принципиально (комиссия 0.3%/сделка = 0.6%/цикл делает короткие сделки убыточными математически).
- **Инструменты**: 2–5 активных бумаг + опционально IMOEX как бенчмарк (не торгуемый, а справочный инструмент).
- **Направление**: только LONG. Шорты исключены из домена полностью (не флагом, а отсутствием кода) — пользователь не готов работать с заёмными позициями.
- **Счёт**: бот работает **только** с отдельным выделенным брокерским счётом (`managed_account_id`), физически изолированным от личных инвестиционных позиций пользователя. Любой вызов на другой account_id запрещён на уровне типов.

### 1.2. Философия управления риском
- Бот **не паникует** по цене, но и никогда не остаётся без защиты. Разделены два механизма:
  - **Hard stop** — цена, аварийный, всегда активен, срабатывает без исключений.
  - **Thesis invalidation** — состояние гипотезы входа (не цена), может закрыть позицию раньше hard stop, если условия, на которых строился вход, перестали быть верными.
  - **Time-based exit** — если тезис не подтвердился за заданный TTL, позиция закрывается по истечении времени, а не по излишнему ожиданию.
- Все издержки (комиссия round-trip 0.6%, спред, возможное проскальзывание) закладываются в фильтр входа **до** генерации ордера: цель сделки обязана превышать издержки с запасом (настраиваемый множитель, по умолчанию ×2).

### 1.3. Аналитический подход
- Мультитаймфрейм: 1D (контекст/bias) → 1H (сетап) → 1m (тайминг входа, стакан).
- Часть индикаторов берётся из API (SMA/EMA/RSI/MACD/BB), часть считается самостоятельно (ATR, VWAP, объёмные, Fibonacci-уровни, confluence-скоринг, корреляция с IMOEX).
- Волновой анализ Эллиотта и XABCD-гармоники — **сознательно исключены из MVP** как субъективные и плохо формализуемые методики; Fibonacci retracement — включён как один из вспомогательных confluence-факторов, не как самостоятельный триггер.
- Анализ стакана — используется только как фильтр точного момента входа на 1m-фрейме (дисбаланс объёма, ширина спреда), не как источник самостоятельных сигналов.

### 1.4. Оценка эффективности и самообучение
- Метрики: не примитивный win rate, а **MFE/MAE, exit efficiency и post-exit drift** (кастомная метрика — что произошло с ценой после закрытия сделки).
- Модуль самоанализа генерирует гипотезы о слабых местах стратегии на основе статистики по историческим сделкам, но **никогда не применяет их автоматически** — только после подтверждения на out-of-sample данных (walk-forward) и ручного одобрения пользователем в GUI.
- Всё, что видел и о чём "думал" бот в момент каждого решения, сохраняется максимально подробно (event-sourced снапшоты) для последующего дата-майнинга паттернов успеха/провала.

### 1.5. Контуры выполнения
- **Sandbox** — обязателен, используется для проверки интеграции и корректности исполнения ордеров.
- **Backtest** — обязателен, основной инструмент оценки качества стратегии, работает по walk-forward методологии на локально сохранённых исторических данных.
- **Live** — включается только вручную, всегда с явной цветовой индикацией режима в GUI.

### 1.6. Хранение данных
- Диск, не RAM — весь объём данных (свечи, снапшоты, журнал, гипотезы) хранится в персистентных файлах на диске, ПК не должен ощущать нагрузку на оперативную память в течение рабочего дня.
- Многоуровневое хранение hot/warm/cold с автоматической архивацией и явным контролем занимаемого места, администрируемым через GUI.

## ЧАСТЬ II. АРХИТЕКТУРА (гексагональная, без фанатизма портов)

### 2.1. Принцип

Порт создаётся только тогда, когда для него реально существует или неизбежно появится вторая реализация. Порты определяются как `typing.Protocol` (структурная типизация), без наследования от `abc.ABC` — адаптер соответствует порту просто имея нужные методы.

Итоговый набор портов (не больше, не меньше):

| Порт | Роль | Адаптеры |
|---|---|---|
| `MarketDataPort` | котировки, свечи, стакан, тех.индикаторы из API | `TBankMarketDataAdapter`, `SandboxMarketDataAdapter`, `BacktestReplayAdapter` |
| `OrderExecutionPort` | выставление/отмена/статус ордеров | `TBankBrokerAdapter`, `SandboxBrokerAdapter`, `SimulatedBrokerAdapter` (backtest) |
| `RepositoryPort` | доступ к hot/warm/cold хранилищу | `DuckDBRepository` |
| `ArchivePort` | перенос данных между слоями хранения | `ParquetArchiveAdapter` |
| `ClockPort` | абстракция времени (тестируемость) | `SystemClock`, `FrozenClock` |
| `NotificationPort` (опционально) | внешние алерты | `TelegramNotifier` |

Driving-адаптеры (управляют ядром извне): Web GUI (FastAPI), CLI.
Driven-адаптеры (ими управляет ядро): T-Bank API, Sandbox, БД, файловая архивация.

### 2.2. SSL/TLS — решение зафиксировано

T-Invest API переходит на сертификаты, подписанные Российским Национальным удостоверяющим центром Минцифры, которые отсутствуют в стандартных доверенных хранилищах ОС — это причина ошибок проверки сертификата, а не баг самого API.

**Решение** (не отключение проверки, а расширение доверия):
1. PEM-бандл Russian Trusted CA скачивается один раз с официального источника, кладётся в `config/certs/`.
2. Для gRPC-канала SDK передаётся через `grpc.ssl_channel_credentials(root_certificates=...)`.
3. Для случайных HTTP-вызовов вне SDK — через `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE` окружения.
4. Полное отключение проверки (`verify=False`) доступно только за флагом `INSECURE_TLS_DEV_ONLY`, физически заблокированным при `env=production`.

Вся эта логика инкапсулирована в одном файле адаптера (`adapters/driven/tbank/tls.py`) и не касается остального проекта.

### 2.3. SDK

Официальный пакет — не устаревший `tinkoff-investments`, а `t-tech-investments`, устанавливаемый из собственного индекса пакетов Т-Банка. Данный SDK предоставляет клиент для взаимодействия с торговой платформой Т-Инвестиции на Python, распространяется свободно и не является официальным коммерческим продуктом стороннего разработчика.

## ЧАСТЬ III. ДОМЕННАЯ МОДЕЛЬ

```python
# core/domain/entities.py

@dataclass
class Instrument:
    uid: str
    ticker: str
    lot_size: int
    is_benchmark: bool = False       # True только для IMOEX

@dataclass
class TradePlan:
    """Гипотеза сделки — не просто сигнал, а полноценный план с условиями жизни."""
    id: UUID
    instrument: Instrument
    entry_price: Decimal
    hard_stop_price: Decimal              # аварийный, никогда не отключается
    target_price: Decimal                 # с учётом min_viable_target (издержки × margin)
    thesis: TradeThesis                   # структурированная гипотеза входа
    thesis_invalidation: InvalidationRule # условие смерти гипотезы (не по цене)
    max_holding_time: timedelta           # TTL идеи
    created_at: datetime
    status: TradePlanStatus               # PROPOSED/ACTIVE/CLOSED/REJECTED

@dataclass
class TradeThesis:
    reasoning_chain: list[ReasoningStep]   # вклад каждого модуля ТА в решение
    confluence_score: float
    timeframe_context: dict[Timeframe, str] # bias по каждому фрейму

@dataclass
class Position:
    instrument: Instrument
    quantity: int
    average_entry: Decimal
    opened_at: datetime
    linked_plan: TradePlan
```

Ключевая идея: `TradePlan` — не эфемерный сигнал, а полноценная сущность с жизненным циклом, которая пишется в БД и служит основой для последующего разбора эффективности (MFE/MAE привязываются именно к ней).

## ЧАСТЬ VII. ХРАНЕНИЕ ДАННЫХ

### 7.1. DuckDB — персистентная, не in-memory конфигурация

Важное уточнение по вашему требованию "не засорять ОЗУ днём": DuckDB не является чисто in-memory базой — при указании файлового пути она полностью поддерживает дисковую персистентность и вытеснение операций, не помещающихся в память, на диск, а не держит весь датасет в RAM. По умолчанию DuckDB может использовать до 80% физической RAM системы для кеширования — это **обязательно** ограничивается явно при инициализации:

```python
# adapters/driven/storage/duckdb_repository.py
conn = duckdb.connect("data/warm/snapshots.duckdb")  # файл, не :memory:
conn.execute("SET memory_limit = '1.5GB'")   # жёсткий потолок под дневную работу ПК
conn.execute("SET temp_directory = 'data/tmp_spill'")  # сброс на диск при нехватке
conn.execute("SET threads = 2")              # не конкурировать с дневными задачами пользователя
```

Это даёт ровно то, что нужно: DuckDB хранит данные как единый файл на диске в сжатом колоночном формате, а не в оперативной памяти, при этом лимит потребления RAM жёстко зафиксирован конфигом и виден/редактируем в GUI.

### 7.2. Многоуровневое хранение

```
data/
├── hot/today.duckdb                # текущий торговый день, полная детализация
├── warm/snapshots_6m.duckdb        # последние ~6 месяцев
├── cold/snapshots/                 # партиционированный Parquet-архив
│   └── year=2026/month=09/instrument=SBER/part-0.parquet
├── trades_history.duckdb           # неизменяемая история закрытых сделок
├── trade_features.duckdb           # денормализованная витрина для самоанализа
├── hypotheses.duckdb                # жизненный цикл гипотез
├── portfolio_state.json            # перезаписываемый снэпшот счёта
├── strategy_configs/               # версионированные параметры ТА по инструменту/фрейму
└── backtest_runs/                  # результаты прогонов
```

Фоновый юзкейс `archive_old_snapshots` переносит hot→warm→cold по расписанию, сжимая старые данные в Parquet при приближении к настраиваемому порогу занятого места на диске.

### 7.3. Снапшоты — event sourcing для дата-майнинга

Каждый цикл анализа (даже "ничего не делать"), каждый вход/выход/отказ фиксируется как связка `MarketSnapshot` (всё, что бот видел: OHLCV по фреймам, все индикаторы, стакан целиком, состояние IMOEX, ключевые уровни) + `DecisionSnapshot` (что решено и почему, включая `reasoning_chain` — пошаговый вклад каждого модуля в итоговый score). Именно это превращает журнал "мыслей" в структурированные данные, пригодные для SQL-запросов по паттернам, а не просто текстовый лог.

## ЧАСТЬ VIII. АНАЛИТИКА ЭФФЕКТИВНОСТИ

### 8.1. MFE/MAE и exit efficiency

Maximum Favorable Excursion измеряет наибольшую прибыль внутри сделки от точки входа до лучшей достигнутой точки; exit efficiency рассчитывается как отношение фактически зафиксированной прибыли к MFE, показывая, какую долю потенциального движения удалось поймать.

### 8.2. Post-exit drift — кастомная метрика проекта

Дополнительно к стандартному MFE/MAE считается **пост-выходной дрейф**: сравнение цены выхода с ценой закрытия сессии/через 1/3 дня после выхода. Именно эта метрика формализует пример пользователя ("закрыл в 10, день закрылся в 25 — провал") и агрегируется по десяткам сделок, а не оценивается по единичному случаю, чтобы не путать системную ошибку стратегии со случайным рыночным шумом.

## ЧАСТЬ IX. МОДУЛЬ САМОАНАЛИЗА

```
core/journal/
├── reflection.py         # доменные сущности Thought, TradeSnapshot
├── hypothesis_engine.py  # генерация и статистическая проверка гипотез
└── advisory.py           # формирование текстовых советов для GUI
```

Жизненный цикл гипотезы: `PROPOSED` (минимум 30 сделок в выборке) → `TESTING` (walk-forward валидация на исторических данных) → `CONFIRMED`/`REJECTED`. Общепринятая защита от переобучения — walk-forward, где параметры находятся на одном сегменте данных и проверяются на другом, ранее не использованном сегменте; walk-forward efficiency ratio выше 0.5 считается приемлемым результатом, а ниже 0.3 сигнализирует о переобучении. Ни одна гипотеза не применяется к боевым параметрам без прохождения этой проверки и ручного одобрения пользователем в GUI.

## ЧАСТЬ X. SANDBOX И BACKTEST

**Sandbox**: работа в песочнице не влияет на реальные данные счёта, позволяет создавать неограниченное количество тестовых счетов, не связанных с реальными торгами на бирже. Используется для проверки корректности интеграции (`SandboxBrokerAdapter`), а не для оценки качества стратегии, так как исполнение в песочнице может не полностью отражать реальное проскальзывание и рыночные условия.

**Backtest**: отдельная пара адаптеров (`BacktestReplayAdapter` + `SimulatedBrokerAdapter`), читающих исторические данные из `cold/`-архива, с явной моделью комиссии (0.3%/сделка), проскальзывания и walk-forward-разбиением на in-sample/out-of-sample сегменты.

Настройки % риска, safety margin над издержками, TTL идей, `managed_account_id` с защитой от случайного изменения.

### 11.4. График
Свечи + индикаторы + Fibonacci-уровни + метки входа/выхода + зона MFE/MAE, переключение фреймов.

### 11.5. Журнал мыслей и самоанализ
Лента `TradeSnapshot`/`Hypothesis` с фильтром по статусу, гистограммы exit efficiency и post-exit drift, кнопка ручного одобрения применения гипотезы.

### 11.6. Backtest Runner
Выбор периода/инструментов, режим walk-forward, сравнение equity curve in-sample/out-of-sample.

### 11.7. **Администрирование БД (новый раздел)**

Отдельный полноценный экран управления хранилищем:
- **Обзор занятого места**: размер по каждому слою (hot/warm/cold) с визуализацией, текущий `memory_limit` DuckDB и его редактирование прямо из GUI.
- **Ручное управление архивацией**: кнопки "архивировать сейчас", "пересжать cold-архив", просмотр расписания автоматического джоба.
- **SQL-консоль только для чтения** (read-only) — возможность выполнить произвольный SQL-запрос к `trade_features`/`snapshots` прямо из браузера для ad-hoc дата-майнинга, без необходимости открывать отдельный DB-клиент.
- **Резервное копирование**: экспорт снапшота БД в архив, восстановление из бэкапа.
- **Политика хранения**: настраиваемые пороги (retention period для hot/warm, порог диска для запуска компрессии), полностью управляемые через GUI, а не хардкод.
- **Журнал аудита**: кто/когда менял параметры БД или стратегии — тот же принцип, что и для риск-настроек.

### 11.8. Безопасность
Kill-switch, аудит действий, управление токенами API без отображения raw-значений.
