# AGENTS.md

Канонические правила работы с этим репозиторием для coding-агентов и LLM.
Составлены по официальному `AGENTS.md` и `SKILL.md` T-Invest Python SDK
([opensource.tbank.ru/invest/invest-python](https://opensource.tbank.ru/invest/invest-python)),
документации [T-Invest API](https://developer.tbank.ru/invest/intro/intro) и
практикам Python 3.14+.

Если задача пользователя противоречит этому файлу — выполняйте задачу, но
**не ослабляйте** требования к секретам и торговым операциям.

## 1. Что за проект

Торговый робот на T-Invest API. Python ≥ 3.14, SDK `t-tech-investments`.

Приоритет источников истины (при расхождении):

1. установленный пакет SDK (`t_tech/invest/grpc/**`) и proto-контракты
   (`protos/t_tech/invest/grpc/**`) — из `site-packages`, если пакет установлен;
2. официальная документация T-Invest API;
3. тесты и примеры текущей версии SDK;
4. `docs/research/**` этого репозитория;
5. всё остальное, включая память модели.

**Не выдумывай** классы, enum, поля и методы SDK. Если определение не найдено —
скажи, что оно неизвестно.

## 2. Импорты и SDK

- Новый код пиши только на `t_tech.invest.grpc`:

  ```python
  from t_tech.invest.grpc import AsyncClient, AsyncSandboxClient, Client, SandboxClient
  from t_tech.invest.grpc.schemas import GetAccountsRequest, PostOrderRequest
  from t_tech.invest.utils import (
      decimal_to_money,
      decimal_to_quotation,
      money_to_decimal,
      quotation_to_decimal,
  )
  ```

- Запрещены: `tinkoff.invest.*` (удалённый неймспейс) и `t_tech.invest.services`
  (устаревшие сервисы до версии 1.0.0).
- Клиент — всегда контекстный менеджер, значение после `as` — **набор сервисов**:
  `services.users`, `services.instruments`, `services.market_data`,
  `services.market_data_stream`, `services.operations`, `services.operations_stream`,
  `services.orders`, `services.orders_stream`, `services.stop_orders`,
  `services.sandbox`, `services.signals`.
- Большинство gRPC-методов принимают `request=SomeMethodRequest(...)`.
  Не переноси keyword-аргументы из старых примеров.
- Не смешивай sync и async. `AsyncClient` ⇒ `async with` + `await` + корректное
  закрытие стримов.
- Не редактируй `*_pb2.py`, `*_pb2_grpc.py`, `*.pyi` — они генерируются.

## 3. Секреты

- Токен — **только** из переменной окружения (например `INVEST_TOKEN`).
- Запрещено: токен в коде, коммитах, документации, фикстурах, логах, сообщениях
  об ошибках, traceback, докстрингах.
- Контур (prod/sandbox) задаётся типизированной конфигурацией, а не промтом,
  не ответом LLM и не рыночными данными.

## 4. Деньги, цены, количество

- Все расчёты денег и цен — только `Decimal`. `float` запрещён в любом расчёте,
  влияющем на заявку.
- На границе API — `Quotation` и `MoneyValue`, конвертация **только** штатными
  `quotation_to_decimal` / `decimal_to_quotation` / `money_to_decimal` /
  `decimal_to_money`. Ручная сборка `units`/`nano` запрещена.
- `quantity` в торговых запросах — **лоты**, не штуки. Размер лота берём из данных
  инструмента.
- Цена нормализуется к шагу цены (`min_price_increment`) **до** создания
  request-модели.
- Облигации: учитывай НКД (`aci_value` — за 1 лот). Фьючерсы и облигации
  котируются в пунктах — стоимость считается по формулам из
  `docs/research/01-tinvest-api.md`.
- Даты — всегда timezone-aware `datetime` в UTC.

## 5. Идентификаторы

- `figi`, `instrument_id`, `instrument_uid` — **не взаимозаменяемы**. Берём ровно
  то поле, которое объявлено в request-модели, и храним тип идентификатора
  вместе со значением.
- Основной идентификатор — `instrument_uid`. `FIGI` — устаревший параметр,
  в опционах не поддерживается.
- `instrument_id` принимает `instrument_uid`, `FIGI` или `TICKER_CLASSCODE`
  (например `T_TQBR`).

## 6. Заявки и идемпотентность

- До сетевого вызова генерируем и **сохраняем** клиентский ключ идемпотентности
  `PostOrderRequest.order_id`.
- Три разных id, не путать:
  - `PostOrderRequest.order_id` — клиентский ключ идемпотентности;
  - `PostOrderResponse.order_id` — биржевой идентификатор;
  - `PostOrderResponse.order_request_id` — возвращённый клиентский ключ.
- При запросе состояния для клиентского ключа используем
  `OrderIdType.ORDER_ID_TYPE_REQUEST`, для биржевого —
  `OrderIdType.ORDER_ID_TYPE_EXCHANGE`.
- Слепой retry мутации запрещён. После таймаута/разрыва: не создаём новый ключ,
  запрашиваем состояние исходной заявки, сверяем открытые заявки и сделки,
  повторяем только доказав, что исходная не принята.
- Уникальность `order_id` отслеживается брокером только за последний месяц.
- read-only запросы можно ретраить с ограниченным backoff.

## 7. Архитектура: разделение ответственности

```
рыночные данные → Strategy → торговое намерение → RiskManager → OrderExecutor → T-Invest API
                                                       ↘ StateStore ↗
```

- `MarketDataProvider` — получение и нормализация данных.
- `Strategy` (в т.ч. LLM) — формирует структурированное намерение, **без сетевых
  мутаций и без вызова `post_order`**.
- `RiskManager` — детерминированно принимает или отклоняет намерение.
- `OrderExecutor` — превращает одобренное намерение в request-модель.
- `StateStore` — клиентские и биржевые id, состояние, результаты сверки.
- `Supervisor` — kill switch и сверка, **в отдельном процессе** от стратегии.

Pre-trade проверки (детерминированные, перед любой мутацией): режим и счёт,
однозначно найденный инструмент, торговый статус и доступность покупки/продажи,
размер лота, шаг цены, количество > 0, доступные средства/позиция, лимиты заявки
и позиции, дневной убыток, тип заявки и обязательные поля request-модели.

Если LLM участвует в принятии решений: ответ валидируется по строгой структуре
до `RiskManager`; текстовый `confidence` не используется как размер позиции;
новости и веб-страницы — недоверенные данные, они не могут менять режим и лимиты;
при ошибке разбора — отказ от сделки.

## 8. Тесты

- Автоматические тесты **никогда** не создают реальных заявок и не трогают
  реальные счета.
- Сетевые тесты песочницы — отдельный маркер `test_sandbox`, не запускаются
  как обычные unit-тесты.
- Обязательные unit-кейсы: валидация намерения, границы размера/позиции/убытка,
  преобразование финансовых типов и округление до шага цены, повторный сигнал,
  таймаут и запрет слепого retry, частичное исполнение, отмена, восстановление
  после перезапуска, запрет перехода sandbox → production через входные данные.

## 9. Python 3.14+ и стиль

- Целевая версия: Python 3.14 (допустимо 3.15 после 2026-10-01). Не используй
  синтаксис новее минимальной версии из `pyproject.toml`.
- Туллинг: `uv` (окружение и зависимости), `ruff` (lint + format), `mypy`
  (strict) или `ty`, `pytest`, `pre-commit`.
- Типизация обязательна в публичных сигнатурах: PEP 695 generics,
  `type Alias = ...`, `Self`, `Protocol` для структурного подтипирования,
  `TypeIs` предпочтительнее `TypeGuard`, `TypedDict`/`NamedTuple`/frozen
  dataclass для DTO.
- Структура — `src/` layout, метаданные и туллинг — в `pyproject.toml` (PEP 621).
- Логирование — структурированное (`structlog`), без токенов и персональных
  данных. Деньги в логах — строкой из `Decimal` с явной точностью.
- Исключения: явные доменные классы, в `except` не «глотать» ошибки молча;
  `return/break/continue`, покидающие `finally`, недопустимы (SyntaxWarning с 3.14).

## 10. Реализация: дополнительные правила

Разделы 1–9 остаются в силе; ниже — правила, возникшие с появлением кода.

### Слои и зависимости

```
adapters/driving (GUI, CLI) → application (юзкейсы) → core (домен)
                              adapters/driven (tbank, sandbox, backtest, storage) → core
config → application → core
```

- `core/` **не импортирует** ничего внешнего: ни SDK, ни DuckDB, ни FastAPI.
- Порты — `typing.Protocol` с `@runtime_checkable`, их ровно шесть:
  `MarketData`, `OrderExecution`, `Repository`, `Archive`, `Clock`,
  `Notification`. Адаптер реализует порт структурно, без наследования.
- `application/` не знает, какой адаптер подключён: выбор делает
  `composition.py` по контуру (`BACKTEST` / `SANDBOX` / `LIVE`).

### Тесты

- Юнит-тест ядра не имеет права трогать сеть, диск и внешние библиотеки —
  для этого есть фейки в `tests/fakes.py`.
- Порт с несколькими реализациями обязан иметь **контрактный тест**: один
  набор проверок гоняется по всем реализациям, включая фейк.
- Изменение конфига стратегии в тестах — только через `StrategyConfig`
  из БД; правка исходников под «подбор параметров» не считается настройкой.

### Опасные места (не ломать)

- `is_select_only` — единственный барьер перед произвольным SQL в GUI.
- Ключ идемпотентности: `build_client_order_id()` вызывается **до** сетевого
  вызова; мутация без ключа не повторяется (`adapters/driven/tbank/retry.py`).
- `_assert_managed_account` — блокировка торговли чужим счётом.
- `monitor_positions.decide_exit` — порядок проверок: hard stop → инвалидация →
  TTL → тейк. Менять порядок нельзя.
- `min_viable_target_multiplier` — фильтр сделок, не окупающих издержки.

### Инструменты

- `ruff` закреплён как `>=0.14,<0.15`: в 0.15/0.16 форматтер ломает
  `except (A, B):`, превращая его в синтаксически некорректный код.
  После `ruff format` имеет смысл прогнать `python -m compileall`.
- `mypy` проверяет только исходники (`tests/` в `exclude`): фикстуры
  намеренно свободны по типам.

## 11. Критерии завершения задачи

- импорты и сигнатуры существуют в текущей версии SDK;
- тесты не обращаются к реальному контуру;
- токены и персональные данные не попали в diff;
- для финансовых значений не добавлен `float`;
- документация различает prod, sandbox и локальные тесты;
- `ruff check`, `ruff format --check`, `mypy` и `pytest -m "not sandbox"`
  проходят;
- выполненные проверки и ограничения окружения перечислены в отчёте.
