## I. Профиль торговли

| Решение | Значение | Обоснование |
| :-- | :-- | :-- |
| Стиль | свинг + интрадей | сделки держатся от часов до дней |
| Направление | **только LONG** | шорты и плечи исключены из кода полностью |
| Размер корзины | 2–5 бумаг | концентрация вместо «индекса из 30 бумаг» |
| Бенчмарк | IMOEX | **не торгуется**, только сравнение силы (relative strength) |
| Счёт | отдельный `managed_account_id` | остальные счета блокируются на уровне адаптера |
| Исключено | HFT, скальпинг, шорты, маржинальные плечи | не реализуются даже «на всякий случай» |

## II. Риск и выходы

Всегда активны **три** механизма выхода:

1. **Hard stop** — защита капитала, ставится всегда, без исключений.
2. **Thesis invalidation** — выход по нарушению логики входа, **не по цене**.
3. **Time exit (TTL)** — идея, которая не сработала в срок, закрывается.

Плюс фильтр **до** отправки ордера:

```
цель (expected_return_pct) ≥ round_trip_costs × min_viable_target_multiplier
```

`min_viable_target_multiplier` по умолчанию = **2**. Сделка, которая не
окупает издержки с двукратным запасом, не открывается.

Правила сайзинга: `Size = (Капитал × Риск%) / |Entry − Stop|`, округление до
лотов **вниз**, риск 1–2% база, потолок 2–5%.

## III. Архитектура

* Гексагональная (ports & adapters).
* Порты — `typing.Protocol` (структурная типизация, без наследования от `ABC`).
* Ровно **6 портов**: `MarketData`, `OrderExecution`, `Repository`, `Archive`,
  `Clock`, `Notification`.
* `core/` **не содержит внешних зависимостей** — только стандартная библиотека
  и `Decimal`.
* Направление зависимостей: `config → application → core`, `adapters → core`.
  Ядро не знает ни про T-Invest, ни про DuckDB.

## IV. Домен

* `TradePlan` — сущность с жизненным циклом:
  `PROPOSED → PENDING → ACTIVE → CLOSED_*` или `REJECTED`.
* `TradeThesis` + `reasoning_chain` — цепочка рассуждений: видно, *почему*
  принято решение.
* `InvalidationRule` — правило инвалидации тезиса (не ценовое).
* Метрики качества сделки: **MFE / MAE / exit_efficiency / post_exit_drift**.
* `Hypothesis` — жизненный цикл `PROPOSED → TESTING → CONFIRMED`;
  минимум **30 сделок** на гипотезу, обязательная **walk-forward** проверка и
  **ручное одобрение** применения.

## V. Анализ

* Мультитаймфрейм: `1D → 1H → 1m` (старший задаёт контекст, младший — момент).
* Индикаторы из API (SMA, EMA, RSI, MACD, Bollinger) + свои (ATR, OBV, VWAP,
  Fibonacci, confluence-скор, корреляция с IMOEX, анализ стакана).
* **Исключены**: волны Эллиотта, паттерны XABCD.
* Confluence-скор — взвешенная сумма факторов с порогом отсечения.

## VI. Хранение

* **DuckDB файловый** (не `:memory:`), с явными `memory_limit`,
  `temp_directory`, `threads` — иначе анализ «съест» всю память процесса.
* **Parquet** для холодного архива.
* Слои **hot / warm / cold**, снапшоты хранятся по принципу event-sourced
  (историю не перезаписываем).
* Чтение через SQL для дата-майнинга, включая read-only консоль в GUI.

## VII. GUI

* FastAPI + WebSocket.
* Раздел администрирования БД с **read-only SQL-консолью**: запрос проходит
  проверку `is_select_only`, мутирующие конструкции и `;` отвергаются.
* Живая лента «мыслей бота» через WebSocket.

## VIII. Контуры

| Контур | Назначение |
| :-- | :-- |
| `BACKTEST` | прогон по истории, реплей + симулятор исполнения |
| `SANDBOX` | песочница T-Invest: реальный сетевой контур, виртуальные деньги |
| `LIVE` | боевой счёт — **только после** чек-листа (см. ниже) |

## IX. Не входит в MVP

Шорты и плечи, Эллиотт и XABCD, авто-применение гипотез, тиковая запись
стакана, поддержка нескольких брокеров.

## X. Критерии приёмки

1. Каждый модуль ядра — с **юнит-тестами без внешних зависимостей**.
2. Каждый порт, имеющий несколько реализаций, — с **контрактными тестами**
   (один набор проверок гоняется по всем реализациям).
3. `LIVE` допустим только после: работы в sandbox + walk-forward проверки +
   **явного решения пользователя**.
