# 01. T-Invest API — полный разбор

Источник: [developer.tbank.ru/invest](https://developer.tbank.ru/invest/intro/intro).
Все цифры и ограничения актуальны на 2026-09-24.

---

## 1.1. Что это и на чём работает

T-Invest API — **gRPC-интерфейс** к торговой платформе Т-Инвестиции. Данные
бесплатны. Через API доступно:

- выставление всех видов поручений — лимитных, рыночных, стоп-заявок;
- рыночные данные, включая исторические: стриминг и unary-запросы;
- портфель, позиции, доходность, операции;
- проверка алгоритмов на истории (механизм бэктеста клиент пишет сам).

**Адреса:**

| Контур | Адрес |
| :-- | :-- |
| Prod | `invest-public-api.tbank.ru:443` |
| Песочница | `sandbox-invest-public-api.tbank.ru:443` |

Протоколы: gRPC (основной) и REST (ограниченно; у части методов ниже лимиты —
например `getHistory` REST — 30 запросов/мин). Для нового кода — только gRPC.

Proto-контракты: [opensource.tbank.ru/invest/invest-contracts](https://opensource.tbank.ru/invest/invest-contracts/-/tree/master/src/docs/contracts).

Требования к старту: открытый брокерский счёт и пройденная идентификация, токен,
понимание идентификаторов инструментов.

## 1.2. Токены

| Тип | Что даёт |
| :-- | :-- |
| Read-only | чтение портфеля, котировок, истории; **заявки выставлять нельзя** |
| Full-access | все методы — основной рабочий токен |
| Transfer-access | full-access + переводы между счетами |
| На конкретный счёт | доступ к одному счёту с настраиваемым уровнем прав |
| Sandbox | только песочница; при обращении к обычным методам — ошибка |

Ключевые факты:

- Токен передаётся в metadata каждого unary-запроса и при установлении любого
  stream-соединения.
- **Срок жизни — 3 месяца с даты последнего использования.** Просрочка → ошибка
  `40003`.
- Токен показывается один раз и банком не хранится.
- В настройках профиля должна быть **отключена функция «Подтверждение сделок
  кодом»**, иначе робот не сможет торговать.
- Сделки свыше **30 000 000 ₽** требуют подтверждения по СМС и через API
  недоступны — крупные объёмы дробим.
- Токенов можно выпускать сколько угодно; логично развести: read-only для
  сбора данных, full-access для торговли, sandbox для тестов.

## 1.3. Модель идентификации инструментов

Иерархия Т-Инвестиций:

```
Бренд (эмитент) → Актив (ценная бумага) → Позиция (актив + площадка)
      → Торговый инструмент (позиция + режим торгов)
```

Котировки можно получить **только по торговому инструменту**.

| Параметр | Смысл |
| :-- | :-- |
| `uid` | идентификатор бренда |
| `asset_uid` | идентификатор актива |
| `position_uid` | идентификатор позиции |
| `instrument_uid` | идентификатор торгового инструмента — **основной** |
| `ticker` | тикер (1–5 символов), сам по себе не уникален |
| `class_code` | режим торгов / секция |

Прочие идентификаторы:

- **ISIN** — 12 символов, международный (у акции T-Технологий — `US87238U2033`).
- **FIGI** — 12 символов. Присваивается внутри Т-Инвестиций и **не всегда
  совпадает с международным классификатором**. Официально помечен как
  **устаревший**; в опционах не поддерживается. Используйте `instrument_uid`.
- Универсальное поле `instrument_id` в большинстве методов принимает
  `instrument_uid` **или** `FIGI` **или** строку вида `TICKER + "_" + CLASS_CODE`.

Пример: `instrument_id = "T_TQBR"` — акции Т-Технологий на Мосбирже.

### Популярные класс-коды

| Код | Что это |
| :-- | :-- |
| `TQBR` | основной режим торгов акциями, MOEX |
| `TQOB` | основной режим торгов облигациями, MOEX |
| `TQTF` | основной режим торгов фондами, MOEX |
| `SPBFUT` | фьючерсы, MOEX (срочный рынок) |
| `SPBOPT` | опционы, MOEX |
| `SPBRU` | акции и фонды, SPB Exchange |
| `CETS` | валюта, MOEX |

Поиск инструмента — метод `FindInstrument` сервиса инструментов (параметр
`query` принимает любой известный идентификатор или название).

> ⚠️ У валюты лотность разная, и это **разные инструменты с разными uid**:
> FIGI доллара с лотностью 1000 — `TCS0013HGFT4`, с лотностью 1 —
> `USD000UTSTOM`. Робот обязан явно выбирать лотность.

### Как приложение работает со справочником

Каталог инструментов **не хранится в коде**: тикеры, названия, размеры лотов и
UID меняются (делистинги, сплиты, новые листинги), и зашитые значения
расходятся с реальностью молча. Поэтому:

1. Справочник загружается из API методами `Shares`, `Etfs`, `Currencies`,
   `Futures`, `Bonds` (запрос — `InstrumentsRequest` со статусом
   `INSTRUMENT_STATUS_BASE`), а точечный поиск — `FindInstrument`
   (`FindInstrumentRequest`: `query`, `instrument_kind`, `api_trade_available_flag`).
2. Полученный каталог сохраняется в DuckDB (таблица `instrument_catalog`) —
   списки ограничены 15 запросами в минуту, поэтому читать их на каждый экран
   GUI нельзя. Момент последнего обновления хранится в
   `operational_settings` (ключ `instrument_catalog:updated_at`).
3. GUI, бэктест и поиск по названию читают каталог из БД. В бэктесте сети нет,
   и адаптер реплея работает только с сохранёнными записями.
4. Разрешение инструмента при добавлении в корзину по-прежнему идёт через
   `GetInstrumentBy`: сохранённая запись не подменяет проверку API.
5. Обновление — по кнопке на `/instruments`, CLI-командой
   `redbot catalog-refresh`, автоматически на старте live/sandbox и раз в 6 часов
   планировщиком (не чаще, чем требует TTL в сутки).

## 1.4. Нестандартные типы данных

### Timestamp

Protobuf `Timestamp`: `Seconds` (с 1970-01-01 UTC) + `Nanos` (от −999 999 999
до 999 999 999). Диапазон: `0001-01-01T00:00:00Z` … `9999-12-31T23:59:59.999999999Z`.
**Всегда UTC.** В Python — timezone-aware `datetime` в UTC, naive datetime
запрещён.

### MoneyValue и Quotation

Оба — «целая часть + миллиардные доли»:

```jsonc
// MoneyValue
{ "currency": "RUB", "units": "114", "nano": 250000000 }   // 114,25 ₽
// Quotation
{ "units": "114", "nano": 250000000 }                      // 114,25
```

Правила:

- `currency` — ISO-4217 (`RUB`, `USD`, `CNY`).
- `nano` — дробная часть, `|nano| < 1_000_000_000`.
- Знаки `units` и `nano` обязаны совпадать: `-0,01` → `units: "-0"`,
  `nano: -10000000`.
- Конвертация **только** штатными функциями SDK (см. `02-tinvest-python-sdk.md`),
  не ручной сборкой.

## 1.5. Формулы расчёта реальной стоимости

Котировка ≠ деньги в рублях. Обозначения: `price` — котировка, `nominal` —
номинал, `lot` — лотность, `min_price_increment` — шаг цены,
`min_price_increment_amount` — стоимость шага цены.

| Инструмент | Стоимость |
| :-- | :-- |
| Акции | `price × lot` |
| Облигации | `price / 100 × nominal`; с НКД: `price / 100 × nominal + current_nkd` |
| Валюта | `price × lot / nominal` (у JPY, AMD, KZT `nominal = 100`) |
| Фьючерсы | `price / min_price_increment × min_price_increment_amount` |

Облигации и фьючерсы котируются **в пунктах**. Для облигаций 1 пункт = 1 %
номинала.

**НКД:** возвращается в `current_nkd` или `aci_value`. `aci_value` — размер НКД
в валюте расчётов **за 1 лот**: при покупке к стоимости сделки добавляется
`aci_value × quantity`, при продаже — вычитается.

Отрицательная цена допустима только для фьючерсов.

## 1.7. Торговые поручения

### Выставление

`postOrder` выставляет и рыночные, и лимитные заявки. Обязательные вещи:

- `instrument_id` — `instrument_uid` или `FIGI` (или `TICKER_CLASSCODE`);
- `order_id` — **клиентский ключ идемпотентности**, генерируется до вызова.

**Идемпотентность.** Если сервис получит несколько запросов с одним `order_id`,
на биржу выйдет **только одно** поручение; последующие вернут ошибку `30057`.
Уникальность значений отслеживается **только за последний месяц** — значит
ключи надо генерировать с гарантированной уникальностью (UUIDv4/v7), а не
«счётчик с утра».

**Три идентификатора, которые все путают:**

| Поле | Где | Смысл |
| :-- | :-- | :-- |
| `PostOrderRequest.order_id` | запрос | клиентский ключ идемпотентности |
| `PostOrderResponse.order_id` | ответ | **биржевой** идентификатор заявки |
| `PostOrderResponse.order_request_id` | ответ | эхо клиентского ключа |

В `getOrderState.order_id` по умолчанию передают биржевой id. Для клиентского
ключа — `order_id_type = OrderIdType.ORDER_ID_TYPE_REQUEST`; для биржевого —
`ORDER_ID_TYPE_EXCHANGE`.

### Получение списка заявок

`getOrders` по умолчанию возвращает **только активные** поручения; исполненная
заявка из выдачи пропадает. Чтобы получить все — `advanced_filters`, но:

- исполненные и отменённые доступны **только за текущий день**;
- интервал запроса не должен превышать **1 час**.

`getOrderState` помимо статуса возвращает стадии исполнения (`stages`), но
**не предназначен для глубокой истории**: по поручениям старше одного дня
информация может не вернуться.

### Отмена и замена

- `cancelOrder` — отмена активного поручения.
- `replaceOrder` — отмена существующего + выставление нового. Если поручение
  нельзя отменить → ошибка `30059` с причиной в `message`.
- Для ускорения есть асинхронный метод выставления — `postOrderAsync`
  (лимит 600/мин против 15/сек у `postOrder`).

### Стоп-заявки

`PostStopOrder` / `GetStopOrders` / `CancelStopOrder`. Ключевой параметр —
`expiration_type`:

- `GoodTillCancel` — активна до отмены;
- `GoodTillDate` — до даты из `expire_date`.

### Денежные ограничения

- Заявка дороже **30 млн ₽** через API невозможна (СМС-подтверждение) → дробим.
- Отрицательная цена — только для фьючерсов.

## 1.8. Торговые статусы

Получить: `GetTradingStatus` или подписка `Info` в стриме котировок.

| Статус | Лимитные | Рыночные | По лучшей цене |
| :-- | :-: | :-: | :-: |
| `UNSPECIFIED` | — | — | — |
| `NOT_AVAILABLE_FOR_TRADING` | — | — | — |
| `OPENING_PERIOD` | ✔ | — | ✔ |
| `CLOSING_PERIOD` | ✔ | — | ✔ |
| `BREAK_IN_TRADING` | — | — | — |
| `NORMAL_TRADING` | ✔ | ✔ | ✔ |
| `CLOSING_AUCTION` | ✔ | ✔ | ✔ |
| `DARK_POOL_AUCTION` | — | ✔ | — |
| `DISCRETE_AUCTION` | ✔ | ✔ | ✔ |
| `OPENING_AUCTION_PERIOD` | ✔ | ✔ | ✔ |
| `TRADING_AT_CLOSING_AUCTION_PRICE` | ✔ | — | ✔ |
| `SESSION_ASSIGNED` | ✔ | — | ✔ |
| `SESSION_CLOSE` | — | — | — |
| `SESSION_OPEN` | ✔ | ✔ | ✔ |
| `DEALER_NORMAL_TRADING` | ✔ | — | ✔ |
| `DEALER_BREAK_IN_TRADING` | — | — | — |
| `DEALER_NOT_AVAILABLE_FOR_TRADING` | — | — | — |

Важные нюансы:

- `BREAK_IN_TRADING` — перерыв, в т.ч. из-за волатильности. Заявки запрещены.
- `DISCRETE_AUCTION` — дискретный аукцион вместо перерыва при высокой
  волатильности; сделок до возобновления торгов нет, расчёта рыночной цены нет.
- `DEALER_*` — режим внутренней ликвидности брокера (торговля по выходным).
  Рыночные заявки недоступны.
- Расписание из `TradingSchedules` — это расписание **секции внутри брокера**,
  оно может не совпадать с биржевым. Для «можно ли сейчас торговать» используем
  `trading_status`.

## 1.9. Рыночные данные

Три способа:

1. **Unary** — история и разовые снимки: `getCandles`, `getLastPrices`,
   `getOrderbook`, `GetTradingStatus`.
2. **Bidirectional stream** (`MarketDataStream`) — реальное время, минимальные
   задержки. Подписки: стаканы (глубина 1/10/20/30/40/50/100), свечи, лента
   обезличенных сделок, торговые статусы, последние цены, свои подписки.
   **Один запрос = один тип данных**: чтобы подписаться и на свечи, и на стаканы,
   шлём два `marketdataRequest`.
3. **Server-side stream** — то же, но одним объектом; нужен для gRPC-web
   (браузерных клиентов).

Особенности:

- Свечи в стриме собираются из ленты сделок в реальном времени и уходят **не
  чаще раза в 100 мс** плюс свеча закрытия периода. Сделки могут прийти после
  закрытия интервала — тогда приходит «корректирующая» свеча. Для гарантированно
  закрытых свечей есть параметр `waiting_close`.
- Сервер шлёт ping — клиенту отвечать не нужно, но **клиент обязан успевать
  вычитывать поток**, иначе соединение разорвут.
- `MarketDataStream` быстрее, чем `getCandles`.
- `getLastPrices` с пустым массивом `instruments` вернёт последние цены по всем
  доступным инструментам.

### История: ограничения `getCandles`

| Интервал | Допустимый период | Макс. `limit` |
| :-- | :-- | --: |
| 5 секунд | 5 сек – 200 мин | 2500 |
| 10 секунд | 10 сек – 200 мин | 1250 |
| 30 секунд | 30 сек – 20 ч | 2500 |
| 1 минута | 1 мин – 1 день | 2400 |
| 2 минуты | 2 мин – 1 день | 1200 |
| 3 минуты | 3 мин – 1 день | 750 |
| 5 минут | 5 мин – неделя | 2400 |
| 10 минут | 10 мин – неделя | 1200 |
| 15 минут | 15 мин – 3 недели | 2400 |
| 30 минут | 30 мин – 3 недели | 1200 |
| 1 час | 1 ч – 3 месяца | 2400 |
| 2 часа | 2 ч – 3 месяца | 2400 |
| 4 часа | 4 ч – 3 месяца | 700 |
| 1 день | 1 день – 6 лет | 2400 |
| 1 неделя | 1 неделя – 5 лет | 300 |
| 1 месяц | 1 месяц – 10 лет | 120 |

Дополнительно:

- Глубина истории различается от инструмента к инструменту и от интервала к
  интервалу. Дата начала истории — поля `first_1min_candle_date` и
  `first_1day_candle_date` в сервисе инструментов.
- Свечи секундных интервалов доступны **только за последний месяц**.
- Максимальный период за один запрос `getCandles` — один календарный год.
- По фьючерсам дневные свечи в API и на бирже расходятся: брокер считает день в
  пределах календарного дня, биржа — от открытия предыдущей вечерней сессии.
- `GetHistory` (ZIP архив минутных свечей за год) обновляется **раз в сутки**,
  текущего дня в архиве нет. Есть готовый скрипт выгрузки по списку
  инструментов за все доступные годы.

## 1.10. Лимиты

**Главное правило:** общая нагрузка не должна превышать **50 запросов/сек** по
всем счетам и токенам с одного адреса. Лимит сервиса — суммарно по всем его
методам и по всем аккаунтам пользователя.

### Unary, запросов в минуту

| Сервис / метод | Лимит |
| :-- | --: |
| Сервис инструментов | 200 |
| `Bonds`, `Shares`, `Options`, `Futures`, `Etfs`, `GetAssets` | **15** |
| Сервис счетов | 100 |
| Сервис операций | 200 |
| Формирование отчётов (сервис операций) | 5 |
| Сервис котировок | 600 |
| Сервис стоп-заявок | 50 |
| Песочница | 200 |
| Сервис заявок | 100 |
| Сервис сигналов | 100 |
| Сервис автоследования | 100 |
| `getHistory` (REST) | 30 |
| `getOrders` | 200 |
| `postOrder` | 15 в секунду (900 в минуту) |
| `cancelOrder` | 300 |
| `replaceOrder` | 300 |
| `postOrderAsync` | 600 |
| `getStopOrders` | 60 |

### Стримы

| Ресурс | Лимит |
| :-- | --: |
| Соединения сервиса котировок | 32 |
| Соединения сервиса заявок | 16 на каждый тип |
| Соединения сервиса операций | 11 на каждый тип |
| Подписок в одном соединении котировок | 300 (суммарно свечи + стаканы + лента) |
| Запросов на подписку | 100 в минуту |

При exceeding 100 запросов подписки в минуту все элементы получают статус
`SUBSCRIPTION_STATUS_TOO_MANY_REQUESTS`.

Счётчик соединений обновляется раз в 2 минуты. `GetUserTariff` может вернуть
лимит на 1 больше — это запас под переподключение, его не стоит выжимать.
Превышения не будет, если с IP идёт меньше 1000 запросов в минуту.
Лимита на число активных заявок нет.

### Троттлинг доставки в стримах

| Подписка | Интервал отправки |
| :-- | --: |
| Trades | без ограничений |
| Orderbook | 100 мс |
| Candles | 100 мс |
| LastPrice | без ограничений |
| Info | без ограничений |

За один интервал по одной подписке уходит только одно сообщение.

## 1.11. Ошибки

Формат: код + gRPC-статус + сообщение. Наиболее значимые:

| Код | gRPC | Что значит | Что делать |
| --: | :-- | :-- | :-- |
| `12001` | UNIMPLEMENTED | метод не реализован | проверить версию контракта |
| `12002` | UNAVAILABLE | метод устарел и недоступен | перейти на новый метод |

## 1.12. Песочница

- Пополнение только в рублях, только на положительную сумму. Выводить и
  уменьшать баланс нельзя. Лимит пополнения — 30 000 000 ₽.
- Счета виртуальные, хранятся **3 месяца** с даты последнего использования и
  могут быть удалены в любой момент.
- Открыты все инструменты, включая требующие статуса квалинвестора. Маржиналка
  и шорты разрешены, плечо для всех = 2.
- Нет начислений купонов и дивидендов, не считаются налоги. Комиссия — ровно
  **0,05 %** от объёма сделки.
- Не считаются ставки риска, ГО, ликвидность портфеля, относительная и
  абсолютная доходность. `GetMarginAttributes` возвращает
  `liquid_portfolio = стоимость портфеля`, `starting_margin = corrected_margin =
  minimal_margin = amount_of_missing_funds = 0`, `funds_sufficiency_level = 2`.
- `GetDividendsForeignIssuer` и `GetBrokerReport` всегда возвращают пустой ответ.

**Эмуляция исполнения (критично для интерпретации результатов):**

- Рыночная заявка исполняется по цене последней сделки.
- Заявка **не влияет на рынок**: заявка на 1 лот и на 10 000 лотов исполнятся
  по одной цене.
- Лимитная заявка при наличии встречного предложения хотя бы на 1 лот
  исполняется **полностью** по цене лучшего встречного предложения.
- Неисполненная лимитная заявка встаёт в рынок и **не участвует в формировании
  стакана**.
- Операции появляются только при исполнении.

Вывод: песочница проверяет **корректность интеграции**, а не прибыльность
стратегии.

## 1.13. Производительность

- Серверы брокера — в дата-центрах M1 и Dataspace. Размещение рядом снижает
  задержки.
- Маржинальная торговля **существенно замедляет** исполнение. Если не нужна —
  отключаем.
- Задержки выставления растут пропорционально числу сделок за день. При десятках
  тысяч заявок в сутки: `postOrderAsync` и/или несколько брокерских счетов с
  равномерным распределением потоков.
- Архитектурно можно выставлять заявки из нескольких программных потоков.
- Обновления приходят с разными задержками; от быстрого к медленному:

  1. `OrderStateStream`, `GetOrders`, `GetOrderState`;
  2. `PositionsStream`, `GetPositions`;
  3. `PortfolioStream`, `TradeStream`, `OperationsStream`, `GetPortfolio`;
  4. `GetOperationsByCursor`.

  Это прямая причина, почему сверка состояния обязательна, а «не пришло
  подтверждение» ≠ «заявка не принята».

## 1.14. Этапы разработки робота (по версии вендора)

1. Сбор и анализ исторических данных.
2. Выдвижение гипотезы (не обязательно человекочитаемой — допускается результат
   обучения модели).
3. Проверка гипотезы на истории.
4. Проверка в реальном времени (песочница).
5. Реальная торговля с мониторингом.

Классификация роботов: по автономности (сигнальные / автоматические), по частоте
(HFT / интрадей / фундаментальные), по цели (прибыль / снижение риска /
оптимизация крупных сделок — TWAP-VWAP-подобное дробление), по пулам
ликвидности (арбитражные / монопульные), по способу принятия решений (парная
торговля на спреде, ML, индикаторные), по инструментам (фьючерсы/опционы).

Риски, которые вендор называет прямо: компетентность в трейдинге и
программировании, убытки от робота (в т.ч. без маржиналки), инфраструктурные
сбои.
